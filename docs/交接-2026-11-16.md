## 3.2 角标验收的硬结论（别改回去）

- **判定只认「上下两条等长长横线 + 行距对」**，不认「横线长」单项：
  单看长度会被建筑边、亮边误伤（库里 `biliart-10096573-7` 有 22px 亮边、
  `floating-city-dreams` 有 36px 建筑边）。全库 24 个样本按这条规则零误报。
- **框按比例算，不写死像素**：`x=0.0074W-4, y=0.0130H-4, w=0.0612W+8, h=0.0495H+8`。
  写死 88×44 只在 1344×768 上准，1080P 会漏。
- **修补顺序不能省**：先备份 `.bak-wm` → 写 `.wm-tmp.mp4` → **再量一次** → 干净才换名。
  少这一步就等于「修了但没验」，回到 11-15 那个问题。
- **没 ffmpeg 不许说「干净」**：`Checked=false` 与 `Clean=false` 是两码事，
  界面必须说清「未验收」。片子要留着（花了钱）。
- **只对云端出的新片自动动手**。主人自己导入的视频一律不碰（托盘里显式点才改）。
- **判定要覆盖「残迹」，不能只认完整角标**：被别的工具补过一半的片子，
  剩下的是一条长横线或「长横线 + 竖边」，以前一路被判成「不用处理」，
  于是残影永远留在桌面上。残迹规则见 `PROGRESS.md` 第二十三节。
- **只认竖线会误伤**：真实画面竖直的建筑边、光柱也很长（库里 53px、25px 都有），
  竖线必须配一条够长的横线才算残迹。
- **验收必须多帧**（1.0 / 0.4 / 2.2 秒）：单帧干净不等于整段干净。
- **备份绝不能被覆盖**：修第二次时把 `.bak-wm` 换成本次输入 = 原始素材永久没了。
  已有备份就另存 `.bak-wm2`。
- **修补前先停播放器**：播放器占着 mp4，`File.Move` 会 sharing violation，
  修完再 `ApplyItem` 恢复。

## 3.3 删除的硬结论（v0.9.8，别改回去）

- `SHFileOperation` 返回 0 **不等于**进了回收站。回收站被关（`NukeOnDelete`）、
  超出该卷配额、网络盘 / 可移动盘上，Windows 会**直接永久删除**、返回值照样 0。
  所以 `Recycle.MoveToRecycleBin` 现在返回 `RecycleOutcome`，删完去
  该卷 `$Recycle.Bin\*\` 数一遍 `$I` 记录，多一条才算 `Recycled`；
  一条子目录都读不到时返回 `Unverified`，不许硬猜。
- `LibraryStore.DeleteUnder` 顺序固定为
  **留副本 `.trash\<时间戳>-<tick>\` → 送回收站 → 按结局记账**。
  确认进回收站才删副本；`Vanished` / `Unverified` 时副本留着当最后退路。
- `Delete` 多一个 `out DeleteReport`（`Recycled / Vanished / Failed / Unverified / TrashDir`）。
  状态栏与日志都按这个账目说话：进了回收站才敢说「可还原」，否则明说「已永久删除」。
- 自检旧断言「原路径消失 → 通过」就是漏掉这个 bug 的那条，已换成「结局必须是 `Recycled`」，
  另加「不存在的路径 → `NotFound`」和「两个文件记账为 `Recycled=2`」。`--guardtest` 17/17。
- 自检会往真实回收站丢东西（临时文件被回收走）。跑完的遗留按前缀
  `.selftest-tmp\` / `wb-guardtest` / `dist\WallpaperManager-*` 可安全清掉，
  11-16 已清 484 条 / 70.75MB。
- **还原回来的图不会自动进 index，靠 `Load` 的散图收编**（只扫 `images\`）。
  删除前会把标题 / 收藏 / 动效存进 `<库根>\.trash\entries.json`，收编时按 id 捡回来；
  读不到存档就退回 `Title = id`。`--guardtest` 20 条覆盖这条链，
  「散图收编」以前完全没有自检，是 11-16 晚才补的盲区。
- **一张图 = 一条回收站记录**（v0.9.10）。回收站是**一个文件一条** `$I`/`$R`，没有
  「一次操作一条」；旧代码把原图和缩略图各送一次，主人看到两条就问「为啥删重了」。
  现在 `AddTarget` 把 `thumbs\` 下的算派生文件，走 `StashDerived` 挪进
  `<库根>\.trash\covers\<id>.jpg`（`DeleteReport.Stashed` 记账），只有主文件进回收站。
  兜底：主文件一个都没删掉时，缩略图仍是唯一内容，照旧送回收站。
  还原后 `Load` 用 `ResolveThumb`：`thumbs\` → 暂存那份 → 原图。**别先看 `ThumbAbs`**，
  散图默认把它指成原图，那样永远轮不到暂存那份（第一版就这么错，自检当场抓到）。
  动态壁纸仍是 2 条（mp4 + 封面），那是两份真实内容，不合并。
- **自检进程不收货**（v0.9.10）。`App.BuddySweepEnabled = !SelfTestArgs()`，
  `SweepBuddyJobs` 第一句就 return。原因：自检里 `VerifyDeliveredVideo` 是
  「跳过验收直接算干净」，于是 16:29 跑 `--badgetest` 时把真实工单的
  `biliart-21242299-3.mp4` 收进了 `D:\Wallpaper`（事后抽帧复核是干净的，但纯属运气）。
  `--guardtest` 有一条看门断言钉住它。**要求：跑任何 `--*test` 前先关掉主程序**，
  否则单实例锁会让自检静默退出（不写日志，表现为「没跑」）。

## 4. 已知坑（新增）

- 跑 `--*test` 前先确认主程序没在运行，否则被单实例锁挡掉、**日志不写**，
  看着像「自检没跑」。跑前把 `TEMP`/`TMP` 指向仓库内 `.selftest-tmp\`。
- **凡是会走 `GenCloud` / `RegenCloud` 的自检，都必须把 `Config.GenChannel` 固定成
  `api` 并还原**。真实配置默认 `buddy`，不固定就会走进积分通道的确认框，
  轻则断言全错（`--cloudflowtest` 第 0 步「取消这单」），重则真弹窗卡死
  （`--clouddialogtest`）。本轮已经踩过两次。
- `--launchtest` 偶尔会因上一项自检的播放器残留报 FAIL；单独重跑即可，
  日志里「开播前没有残留播放器」为 √ 就说明是环境残留，不是代码问题。
- `--guardtest` 的回收站断言会把 2 个几十字节测试文件送进系统回收站
  （建在 `.selftest-tmp` 下），清空回收站即可。
- **`export TEMP=... TMP="$TEMP"` 是错的**：同一条 export 里的 `$TEMP` 展开的是**旧值**，
  结果 `TMP` 仍指向真实临时目录，而 .NET 的 `Path.GetTempPath()` 先读 `TMP` ——
  日志会跑到工作空间外。必须分两句写，或 `export TEMP=...; export TMP=...`。
  本轮踩过一次，日志落在真实 `%TEMP%\wallpaper-debug.log`（仅追加日志，无其它改动）。
- **自检断言名 / 输出里别出现 `×`**：所有 `--*test` 的判 PASS 逻辑是
  「detail 里不含 `×`」，一个「1344×768」就会让 18/18 全过却报 FAIL。
  尺寸统一写 ASCII 小写 `x`。
- **`--genapicheck` 已收进 `SelfTestArgs()` 闸门**（11-16 修）。以前它名字不以 `test`
  结尾，判不出来，于是照常恢复动态壁纸、拉起播放器，还顺手把真实库
  `D://Wallpaper//index.json` 的 mtime 改写掉（内容与 `.bak` 逐字节相同，但这就是
  「自检碰了工作空间外的文件」），同时保存了一次 `appdata\config.json`。
  现在跑它不动壁纸、不写库、不存配置。**以后新增任何 `--*` 检查项，务必确认
  名字以 `test` 结尾，或像它一样显式加进闸门。**
- 四个会写真实库/配置的自检（`--deltest / --greettest / --configtest /
  --arrivetest`）默认不跑；`--cloudtest` 会写死工单，永远别跑。

## 6. 11-16 晚新增的硬结论（v0.9.9 → v0.9.11，别改回去）

- **删壁纸必须连片子一起删**：`LibraryStore.Delete` 现在用
  `RelatedVideo.LocateReadOnly` 定位 `videos\<id>.mp4` 并送回收站，
  `DeleteReport.Videos` 记账。用 `LocateReadOnly` 而**不是** `Find` ——
  `Find` 命中散片时会把文件复制成规范名，删除流程不要这种副作用。
  缩略图仍不进回收站（`thumbs\` 下的都算派生文件，挪 `.trash\covers`）。
- **确认框要说实话**：`App.HasRelatedVideo()` 只读探测，有片就写
  「图片和视频会一起移入回收站」。只看 `Motion` 标记会漏（有片但没标动效的条目一样会带走片子）。
- **解码器打开方式要记忆**：`MfVideo.Reader.lastGoodCombo` 记住上次成功的组合。
  `PlayerVideo` 每播完一轮都重开解码器，不记忆就每轮先撞一次
  `0xc00d36b4`（H.264 只吐 NV12，RGB32 必然失败）。
  自检观察点：`Reader.LastAttempts` / `LastGoodName`，`--contenttest` 断言「第二次只试 1 种」。
- **自检不许污染回收站**：`Recycle.TestNoRecycle` 在 `App.Initialize` 里按
  `SelfTestArgs()` 置位 → 自检造的文件一律硬删。guardtest 需要真验回收站时临时关掉，
  断言后 `Recycle.PurgeRecordsFor(path)` 精确清掉自己那几条 `$I/$R`。
- **4K 换片必须先验真实分辨率**：`Online.Upgrade` 下到 `.part4k` →
  `ProbeSize`（MF 读 Width/Height）→ **宽度 >= 3000 才换**，否则删临时文件、原片不动。
  旧片改名 `.bak-4k`，已有就 `.bak-4k2`，绝不覆盖。
  绝不允许「文件变大就当成 4K」——站点可能返回 404 页面或还是 1080P 的片子。
- **本机屏幕是 1920x1080**（日志 `[1] 屏幕 1920x1080`），4K 视频在本机看不出差别，
  所以 `Prefer4k` 默认关、只做逐张手动升级；别默认把主人的带宽和磁盘翻 4 倍。
